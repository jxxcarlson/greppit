# zku IDs — Phase 1 — Schema + Backfill Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add `users.username` and `snippets.zku_id` columns (each `UNIQUE NOT NULL`), populated from a deterministic backfill, with zero data loss and no change to existing API or application behavior. This phase is pure schema + data migration. No Haskell or Elm code is touched.

**Architecture:** A single dbmate migration (`003_add_username_and_zku_id.sql`) runs inside a transaction and follows a three-step pattern per column: **ADD nullable → backfill via a window-function query → tighten to `NOT NULL UNIQUE`**. Collision resolution uses `ROW_NUMBER() OVER (PARTITION BY base ORDER BY created_at, id)` for stable, reproducible ordering. The migration has a working `migrate:down` that fully reverses itself.

**Tech Stack:** PostgreSQL, dbmate, psql.

**Scope:**
- `users.username TEXT UNIQUE NOT NULL` — backfilled from `lower(regexp_replace(split_part(email,'@',1), '[^a-z0-9]', '', 'gi'))` with numeric suffix (`alice`, `alice2`, `alice3`) on collision.
- `snippets.zku_id TEXT UNIQUE NOT NULL` — backfilled from `username || '-' || to_char(created_at AT TIME ZONE 'UTC', 'YYYYMMDDHH24MISS')`, with `-2`/`-3` suffix on collision.
- `snippets.id` (UUID) is unchanged and remains the PK.
- No application code changes in this phase. Minting on insert, API exposure, and UI use all come in Phase 2+.

**Out of scope (deferred plans):**
- Phase 2: signup mints `username`, snippet create mints `zku_id` (writes).
- Phase 3: API surfaces `zkuId` and accepts it for lookup (reads).
- Phase 4: UI display polish.
- Eventually: retire `snippets.id`.

## Task 2: Write validation queries (the "tests" for this migration)

**Why:** A migration is correct iff a fixed set of post-conditions hold on the data. Writing the assertions first (SQL TDD) makes the migration's goal precise and its success observable.

**Files:**
- Create: `backend/dbmate/validation/003_validation.sql`

- [ ] **Step 1: Write validation SQL**

Create `backend/dbmate/validation/003_validation.sql`:

```sql
-- Assertions that must hold on any DB after migration 003 runs.
-- Each DO block raises if an invariant fails.

-- A1: every user has a non-empty username
DO $$
DECLARE bad int;
BEGIN
  SELECT COUNT(*) INTO bad FROM users WHERE username IS NULL OR username = '';
  IF bad > 0 THEN RAISE EXCEPTION 'A1 FAIL: % users with null/empty username', bad; END IF;
END$$;

-- A2: usernames are unique
DO $$
DECLARE bad int;
BEGIN
  SELECT COUNT(*) INTO bad FROM (
    SELECT username FROM users GROUP BY username HAVING COUNT(*) > 1
  ) d;
  IF bad > 0 THEN RAISE EXCEPTION 'A2 FAIL: % duplicate usernames', bad; END IF;
END$$;

-- A3: usernames only contain [a-z0-9] with optional trailing digits (suffix)
DO $$
DECLARE bad int;
BEGIN
  SELECT COUNT(*) INTO bad FROM users WHERE username !~ '^[a-z0-9]+$';
  IF bad > 0 THEN RAISE EXCEPTION 'A3 FAIL: % usernames with illegal chars', bad; END IF;
END$$;

-- A4: every snippet has a non-empty zku_id
DO $$
DECLARE bad int;
BEGIN
  SELECT COUNT(*) INTO bad FROM snippets WHERE zku_id IS NULL OR zku_id = '';
  IF bad > 0 THEN RAISE EXCEPTION 'A4 FAIL: % snippets with null/empty zku_id', bad; END IF;
END$$;

-- A5: zku_ids are unique
DO $$
DECLARE bad int;
BEGIN
  SELECT COUNT(*) INTO bad FROM (
    SELECT zku_id FROM snippets GROUP BY zku_id HAVING COUNT(*) > 1
  ) d;
  IF bad > 0 THEN RAISE EXCEPTION 'A5 FAIL: % duplicate zku_ids', bad; END IF;
END$$;

-- A6: every zku_id begins with an existing username followed by '-'
DO $$
DECLARE bad int;
BEGIN
  SELECT COUNT(*) INTO bad
  FROM snippets s
  JOIN users u ON u.id = s.user_id
  WHERE s.zku_id NOT LIKE u.username || '-%';
  IF bad > 0 THEN RAISE EXCEPTION 'A6 FAIL: % zku_ids not prefixed by owner username', bad; END IF;
END$$;

-- A7: the timestamp segment of each zku_id matches the UTC-formatted created_at
--     (modulo the '-N' suffix on collisions)
DO $$
DECLARE bad int;
BEGIN
  SELECT COUNT(*) INTO bad
  FROM snippets s
  JOIN users u ON u.id = s.user_id
  WHERE SUBSTRING(s.zku_id FROM LENGTH(u.username) + 2 FOR 14)
     <> to_char(s.created_at AT TIME ZONE 'UTC', 'YYYYMMDDHH24MISS');
  IF bad > 0 THEN RAISE EXCEPTION 'A7 FAIL: % zku_ids with wrong UTC timestamp segment', bad; END IF;
END$$;

-- Summary row count for eyeballing
SELECT 'users' AS tbl, COUNT(*) AS rows FROM users
UNION ALL
SELECT 'snippets', COUNT(*) FROM snippets;
```

## Task 3: Write the migration

**Files:**
- Create: `backend/dbmate/migrations/003_add_username_and_zku_id.sql`

- [ ] **Step 1: Write the migration SQL**

```sql
-- migrate:up

-- dbmate wraps each migration in its own transaction, so no explicit
-- BEGIN/COMMIT here: doing so produces `unexpected transaction status idle`.

-- === Users: add username =======================================

ALTER TABLE users ADD COLUMN username TEXT;

-- Sanitize email local-part to [a-z0-9], resolve collisions with numeric suffix.
-- Suffix ordering is deterministic: (created_at, id).
WITH base AS (
  SELECT
    id,
    LOWER(REGEXP_REPLACE(SPLIT_PART(email, '@', 1), '[^a-z0-9]', '', 'gi')) AS base_name,
    created_at
  FROM users
),
numbered AS (
  SELECT
    id,
    base_name,
    ROW_NUMBER() OVER (PARTITION BY base_name ORDER BY created_at, id) AS rn
  FROM base
)
UPDATE users u
SET username = CASE WHEN n.rn = 1 THEN n.base_name
                    ELSE n.base_name || n.rn::text END
FROM numbered n
WHERE u.id = n.id;

-- Guard against an email whose local-part sanitizes to empty (e.g. "+@a.com").
-- Fail loud here rather than let NOT NULL fire cryptically.
DO $$
DECLARE bad int;
BEGIN
  SELECT COUNT(*) INTO bad FROM users WHERE username IS NULL OR username = '';
  IF bad > 0 THEN
    RAISE EXCEPTION 'Migration 003: % users produced empty usernames; inspect users.email before retrying', bad;
  END IF;
END$$;

ALTER TABLE users ALTER COLUMN username SET NOT NULL;
ALTER TABLE users ADD CONSTRAINT users_username_key UNIQUE (username);

-- === Snippets: add zku_id ======================================

ALTER TABLE snippets ADD COLUMN zku_id TEXT;

-- <username>-<YYYYMMDDHH24MISS UTC>, collisions suffixed -2, -3, ...
WITH base AS (
  SELECT
    s.id,
    u.username || '-' || to_char(s.created_at AT TIME ZONE 'UTC', 'YYYYMMDDHH24MISS') AS base_id,
    s.created_at
  FROM snippets s
  JOIN users u ON u.id = s.user_id
),
numbered AS (
  SELECT
    id,
    base_id,
    ROW_NUMBER() OVER (PARTITION BY base_id ORDER BY created_at, id) AS rn
  FROM base
)
UPDATE snippets s
SET zku_id = CASE WHEN n.rn = 1 THEN n.base_id
                  ELSE n.base_id || '-' || n.rn::text END
FROM numbered n
WHERE s.id = n.id;

ALTER TABLE snippets ALTER COLUMN zku_id SET NOT NULL;
ALTER TABLE snippets ADD CONSTRAINT snippets_zku_id_key UNIQUE (zku_id);

-- migrate:down

ALTER TABLE snippets DROP CONSTRAINT IF EXISTS snippets_zku_id_key;
ALTER TABLE snippets DROP COLUMN IF EXISTS zku_id;

ALTER TABLE users DROP CONSTRAINT IF EXISTS users_username_key;
ALTER TABLE users DROP COLUMN IF EXISTS username;
```

## Appendix: Production Deploy Notes (Digital Ocean)

Do not deploy to prod from within this plan — production deploy is a follow-up step after the branch is merged to `main`. These notes capture what to do when that happens.

**Why Phase 1 is low-risk on prod:**
- No app code changes — the running backend does not reference `username` or `zku_id`, so the migration can apply without a restart.
- The migration is transactional (`BEGIN`/`COMMIT`). Any failure rolls back atomically.
- `migrate:down` is implemented and tested in dev.

**Prod deploy sequence:**

```bash
# On the Digital Ocean server, as root (or the greppit user):

# 1. Safety backup. Dump goes to ~/greppit/backups/.
scripts/db-dump-do.sh

# 2. Pull the merged migration.
cd ~/greppit
git pull

# 3. Apply the migration. scripts/migrate.sh reads DATABASE_URL from .env.
scripts/migrate.sh up

# 4. Run the validation assertions against prod.
psql "$DATABASE_URL" -f backend/dbmate/validation/003_validation.sql

# 5. Restart is optional for Phase 1 (no app code changed), but harmless:
systemctl restart greppit-backend
systemctl status greppit-backend
```

**If prod has user emails that sanitize to empty** (e.g. `+@example.com`), the migration's guard will `RAISE EXCEPTION` and roll back. Fix by manually UPDATE-ing the offending `users.email` to something sane, then retry `migrate.sh up`.

**Rollback on prod:**

```bash
scripts/migrate.sh down
# Or, worst case, restore from the dump taken in step 1:
psql "$DATABASE_URL" < ~/greppit/backups/<dump-filename>.sql
```

**Phases 2 and 3 will require the restart** (they add code that reads the new columns). Phase 1 does not.
